# 同族任务加速作业指引

> 依据：2026-10-12 任务 0001/0002（运营周报/月报）复盘。目标：同族新模块全流程从 ~3h 压到 1~1.5h，纯模板复用型模块 30~40min。
> 适用边界：仅用于与已交付模块**同范式**（CUSTOM 业务表单+审批流）的任务；新模式/新集成仍走完整核证。

## 1. 范式复用快速通道（架构阶段）

首例任务（如 0001 周报）完成 10 层源码核证后，其结论在**同仓库内持续有效**。同族第二例起，架构师只做**差异核证**：

| 差异核证项（必做） | 复用项（不再重证） |
|---|---|
| 表结构与首例的字段类型差异 | CUSTOM 全链路范式（DO/Mapper/Service/Provider/Controller 分层） |
| 流程节点链与候选人策略差异 | FormProvider 路径绑定机制、deploy-models.sh 部署链 |
| 特有交互（如 Word/导入/公式） | leave 三件套前端范本、registerComponent 挂载、BaseDO 审计列规范 |

- 架构 prompt 直接给出首例任务目录路径，注明"§X 已核证结论直接采信，只核差异"
- 预期收益：第二例起架构 75min → 20~30min

## 2. 代码模板化（开发阶段）

首例交付的代码族就是活模板。同族任务开发时：

- 陈牧以首例文件为底（如 BpmOpWeeklyReport* → 新模块名词替换），**列明替换映射表**（类名/表名/权限串/菜单段/错误码段/路由/模型 key）
- 长期方案：将首例代码族抽成本地生成脚本（输入表结构→产出全套），在陈牧角色包成熟后沉淀
- 预期收益：单模块后端+前端 33min → 15min 内

## 3. 环境常驻（全局）

任务开始前确认/一次性准备，任务中零等待（以下为本机实测环境记录，跨同事使用时按各自环境校准）：

- 后端服务 IDEA 常驻（或后台 fat jar：`nhxk-server.jar`，**注意 `nhxk-server-boot.jar` 无主清单不可执行**；JDK 版本以仓库 pom 要求为准，本机为 corretto-25）
- 前端 `pnpm dev` 常驻（默认 5173）；MySQL/Redis 常驻
- 若 shell 配置了 HTTP_PROXY 指向本机代理，curl 访问本机服务须加 `--noproxy '*'`（否则"连接失败"是代理假象；本机实测代理为 127.0.0.1:55000，其他同事环境按实际检查）
- DB 凭据读 application-local.yaml；演示/测试账号密码变更须在 00 台账登记
- 新增类需服务重启才能加载（热替换不加载新类）——重启安排在交付验证前一次性做

## 4. 门控合并呈报

- 同族多任务（如周报+月报+季报）**并行推进时，G1 合并为一次多方案呈报**（多问题卡片一次收集全部裁决）；G2 同理
- 门控等待期间不闲置：并行跑另一任务的独立阶段（苏澄基线核对/静态测试可先行）

## 5. 任务下发防并发返工

- 2026-10-12 教训：SendMessage 投递回执超时但消息实际送达 → 唤醒了暂停实例 → 双实例并发写文档 → 归并整改损失 ~30min
- 规则：**成员任务变更尽量在 spawn prompt 一次性下发完整上下文**；避免对可能仍在运行的实例发"改派/叫停"类消息——发现回执超时应先探测实例状态（文件 mtime/任务清单）再决定重派
- 双写检查纪律：文档冲突核验须**全文扫描**"当前有效"标记计数，不能只看文件尾部（grep 漏判教训）

## 6. 不可压缩项（红线）

G1/G2 用户门控、缺陷闭环（发现→修复→复测）、审核独立实查、00~09 文档链（简单任务可瘦身不可省略）。

## 7. 预期基线

| 任务类型 | 目标耗时 |
|---|---|
| 同族新模块（有首例范式） | 1~1.5h |
| 纯模板复用型（字段级差异） | 30~40min |
| 新范式/新集成 | 按首例完整流程（不设压缩目标） |
