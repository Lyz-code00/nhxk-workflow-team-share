# 专项需求检查

仅在需求涉及对应能力时读取相关小节；不要求每个表单具备这些能力。字段单位、审批节点、模板和页面规则来自当前已确认需求，不设业务默认值。

## 必要业务要点

| 主题 | 要确认的具体规则 |
|---|---|
| 关联主体 | 业务主体ID/组织ID如何选择及关联；“记录标题”“显示名”“主数据名称”是否不同；改名称是否影响关联或主数据 |
| 期间与唯一性 | 固定周期还是任意区间；起止日是否含边界、时区、跨月年、未来期间；同业务主体同期间能否重复、重叠、补报或修订 |
| 字段与校验 | 持久化值/展示值/计算值/正文文本分开；暂存与提交必填区别；最大长度、金额单位、精度、范围、负值与空值 |
| 列表查询 | 模糊还是精确匹配；区间按包含还是相交；默认范围、排序、分页；刷新保留哪些条件；名称和组织按快照还是最新主数据 |
| 状态与操作 | 展示状态与内部状态分别定义；草稿/审批中不能只因同名就共用权限；退回目的节点、重提、撤回/取消/终止区别、归档是否人工任务 |
| 节点和权限 | 每节点角色来源、无人/多人/自审处理、意见必填、申请人确认的含义；按钮/API/附件/导出权限和组织与业务数据范围 |
| 历史与并发 | 首次提交与每次提交时间、审批内容快照、修改版本、并发编辑、重复请求、归档后更正及历史可见性 |

## 自动取数与计算

每个取数规则记录：来源模块/接口、匹配键、纳入状态、业务日期、区间边界、去重/冲销退款、单位换算和舍入、公式、零与空值、异常处理、触发时点及快照时点。

专门询问：换关联主体/期间是否重新取数？人工改值后刷新是否覆盖？计算输入改变是否重算派生值？多个异步响应是否可能把旧期间数据写入当前表单？审批和归档查看快照还是实时数据？接口失败与“确实为零”不能混同。

金额需区分结构化数值与叙述文本：列表、统计和正文从哪个值生成，人工改正文会不会改金额；不要默认用正则从自由文本提取正式金额。

## 文书与附件（按需）

- 模板版本、原件下载、默认内容是否可算有效正文；保留示例年份、空白占位与自动回填分别约定。
- 支持的文件格式、大小、正文长度计算方式；导入替换还是追加，失败回滚、重复导入、未保存退出提示。
- DOCX 转换保留哪些字体/表格/图片/分页；HTML 清洗、外部资源、导出扩展名/MIME、命名、正文版本与版式验收样本。
- 表单字段、正文、导出是否联动；某字段独立保存时不可因导入正文而覆盖。
- 附件格式/数量/单个与总大小、重名、上传中提交、部分失败、删除/下载/预览权限、关联与保留期限。

## 证据和范围

区分“原型有按钮”“实际能力”“首期交付”。外部接口、共享脚本或模板缺失时记录依赖，不能把演示数据当已接入。开发备注是否进入正式页面需确认，不默认为产品功能。

产出一张追踪表即可：`编号 | 来源章节/原型位置 | 原有要求或冲突 | 缺口与影响 | 建议选项 | 确认结果 | 验收场景`。阻塞开发的业务选择集中确认；技术路径由架构查证，可逆展示细节列建议，不要求用户回答代码细节。
