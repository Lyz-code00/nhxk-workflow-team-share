# 需求契约

供需求人员内部核对；只将方案和缺失问题集中交给用户确认，不要求用户填写技术大表。已有确认需求只补差异。

| 要点 | 要落实的业务信息 |
|---|---|
| 业务目标 | 谁在什么情况下填写，解决什么问题 |
| 字段 | 标签、含义、类型、必填、校验、单位/精度、默认值、数据来源 |
| 控件 | 日期、选择器、附件、子表等实际需求与平台支持情况 |
| 审批 | 节点顺序、审批人来源、会签/或签、分支条件、自选审批人 |
| 权限 | 谁能发起、查看、修改，节点字段读写权限，租户/部门范围 |
| 生命周期 | 何时提交，能否暂存、撤回、驳回修改、重提，终态行为 |
| 存储与集成 | 是否需要独立业务记录、列表、报表、外部取数/回写或独立留存 |
| 验收 | 各主流程、条件分支、校验失败、权限拒绝的预期结果 |

## 默认与确认

- 默认 **NORMAL**：表单数据随流程保存，复用平台页面。出现独立业务能力要求时先评估 NORMAL 能力，无法满足时提出扩展或 CUSTOM 方案，经用户确认后切换。
- 文案、字段排列等展示细节可以提出可逆建议；字段业务含义、必填规则、金额单位、精度、审批链、身份和权限不能自行猜。
- 审批人可确认选择策略（如部门负责人），实际角色编码/用户编号由架构或开发查证；不要迫使需求用户提供技术编号。
- 技术标识、路由、表名由架构/开发按现有约定提出；NORMAL 不要求独立业务表或 CRUD 菜单。
- 交付范围有裁剪时说明影响并确认。既有环境/身份信息优先查证，证据不足时集中询问。

## 最小确认单

业务目标与范围、表单模式（默认 NORMAL）、字段表、审批规则、权限/生命周期、验收场景、待确认问题。注明需求来源与用户确认依据；未确认不得标记为已确认。

字段表按需包含：标签 / 字段含义 / 控件或类型 / 必填与校验 / 单位精度 / 默认值 / 数据来源。

验收按实际模式和生命周期编写：NORMAL 不强制草稿/业务状态回写；CUSTOM 创建即提交不强制暂存。通过、驳回、取消、重提等仅在约定支持时覆盖，不凭清单增加业务能力。

## 文档输入与需求补全

先区分已明确规则、文档矛盾、缺失规则和演示行为，保留来源章节。补充检查主体关联、周期/重复规则、查询语义、状态映射、接口失败、数据快照、附件与正文、版本及审计；涉及周期数据、自动取数、文书或附件时读取[专项需求检查](专项需求检查.md)。将必要缺口变成集中确认问题，不将补充建议自动写成已确认需求。
