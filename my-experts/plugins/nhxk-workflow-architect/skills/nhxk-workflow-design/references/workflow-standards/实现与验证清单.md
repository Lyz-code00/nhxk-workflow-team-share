# 实现与验证清单

默认 NORMAL，只检查当前模式和本次改动相关项。CUSTOM 仅用于已确认的独立业务需求；生命周期遵循确认方案，不一律要求草稿。执行授权统一遵守 RULES.md，E2E 与留痕见 [测试与留痕标准](测试与留痕标准.md)。

## NORMAL 交付物

- 稳定的字段键与 form-create `conf`/`fields` JSON。
- 已创建的动态表单，或未应用的导入/API 产物。
- 只引用已声明变量的 SIMPLE JSON 或 BPMN XML。
- 表单类型为 NORMAL、`formId` 正确的模型元数据。
- 各节点字段权限与候选人配置。
- 部署已显式执行，或显式保留待执行。

不得仅为镜像 Flowable 变量而给 NORMAL 表单建业务表。

## CUSTOM 后端交付物

- `sql/kingbase/`（生产方言）与 `sql/mysql/`（本地/测试验证）下的版本化迁移，与全量初始化分开，双方言列结构按各自惯例保持一致。
- 业务表、注释、索引、必要的序列、租户/逻辑删除/审计字段，以及流程绑定字段。
- 菜单与按钮权限，编号从当前迁移记录查证、无冲突。
- DO、Mapper、Service 接口/实现、Controller、请求/响应 VO、错误码与测试。
- `selectByIdForUpdate` 行锁，以及按主键+流程实例号匹配的条件状态更新。
- `BpmBusinessFormProvider` 注册、非敏感摘要与状态回写。
- 通过 `BpmBusinessProcessApi` 以稳定业务主键和最小变量发起；同一事务内绑定返回的实例号与 RUNNING 状态，拒绝非可编辑状态的重复提交。
- 摘要最多三个非敏感字段；过期流程事件不能覆盖当前实例状态。
- 只读工作流详情：先核对当前流程绑定，再校验普通业务查询权限或 `BpmProcessPermissionApi` 参与权限。
- 模块 POM 按需依赖现有单 JAR `nhxk-module-bpm`，不新建 bpm-api 子模块；调用 `api.*` 公共契约，可复用现有状态枚举。

保存、分页、提交、普通响应与工作流详情契约不同时使用独立请求模型。不得直接暴露 DO。

## CUSTOM 前端交付物

- 带类型的 API 模型，按需提供 create/update/delete/page/get/get-for-bpm/submit 调用。
- 列表页：状态展示、权限控制与按状态可见的操作。
- 发起/编辑页：校验完整，需要时支持发起人自选审批人。
- 只读工作流详情组件：经现有动态加载契约接收 `businessKey` 与 `processInstanceId`。
- 隐藏的发起/详情路由与正确的 `activeMenu`。
- 不得做仅客户端的授权假设；后端始终是权威。

非平凡 Vue 功能应保持路由视图为组合层，抽出聚焦的表单/详情/列表组件或 hooks。

## 流程交付物

- Provider process key、BPMN/SIMPLE 流程 ID 与已部署定义 key 完全一致。
- 起止事件、命名用户任务、受支持的审批人策略与已声明条件。
- 类型稳定的匹配变量；Flowable 变量中不得携带业务对象图。
- CUSTOM 模型绑定从已注册业务表单列表选择，发起/查看路径不得另行手输。
- 部署是获授权的运行期操作，绝不以迁移方式写入 Flowable 内部。
- 模型 JSON 随仓库交付：`scripts/workflow-models/{processKey}.json` 与 `deploy-models.sh` 入口；跨环境部署前核对管理人、审批人编号等数字身份（同一套基础数据可直接复用，不同编号体系须先替换）。

## 后端验证

只运行用户明确授权的检查。未来获得测试授权时覆盖：

- 已确认需要草稿时的状态初始化；
- 可编辑/禁止状态下的更新与删除；
- 行锁保护的提交与重复提交拒绝；
- formCode、业务主键、变量白名单与返回实例绑定；
- Provider 注册唯一性与摘要数量限制；
- 当前实例与过期实例号的状态回写；
- 业务权限、参与者、非参与者与过期绑定的工作流详情；
- 有隔离金仓环境时的迁移兼容性检查；
- 生成流程产物的 Flowable 解析/部署行为。

## 前端验证

在已有授权范围内运行聚焦的 lint/类型检查与仓库既有测试。验证长整型 ID 在精度敏感处保持字符串、路由路径一致、表单校验可用、按状态的操作是推导而非复制。

除非用户明确要求，不打开浏览器。

## 提交门槛

被要求提交前：

1. 读 RULES.md，核对用户的编译/测试/启动/发布范围。
2. 只执行获授权的检查；编译通过不等于启动通过。
3. 被禁止或不可用的运行期/数据库检查记为待执行。
4. 以中文提交说明提交范围内改动；未经授权绝不推送。
5. 未经要求不更新父仓库引用指针。

## 交付证据

列出生成的文件与标识符、执行的检查及数量/结果、启动证据、未执行的运行期/数据库步骤。保持以下标签区分：

- 已生成；
- 静态验证；
- 测试验证；
- 启动验证；
- 数据库已应用；
- 模型已部署；
- 端到端审批已验证。

## 部署准备与闭环验收

开发负责在任务目录 `08-部署与验收.md` 准备可执行步骤，实际执行仍遵守授权：

1. 核对目标环境、代码版本、数据库方言/迁移、配置与身份映射、数据备份/回退前提；不把测试账号和 ID 直接用于其他环境。
2. 按实际依赖安排服务/迁移/表单/模型/权限菜单的发布顺序。NORMAL 先创建或更新表单取得真实 formId，再绑定模型；CUSTOM 先保证 Provider 和对应接口/页面可用，再绑定模型。
3. 模型创建/更新及部署前核对当前 key/版本和重复执行行为，部署后回读激活定义、表单绑定与节点配置。对已有运行实例说明兼容与处理策略，不默认自动迁移旧实例。
4. 执行已授权的发起、待办、审批、分支、详情/历史、权限及 CUSTOM 状态回写验证；回退需说明已产生实例/业务数据的处理，不能只回滚代码。
5. 保存执行时间、执行范围、实际版本/标识、结果及证据、未执行项。开发完成表示产物满足范围，端到端通过需要真实测试证据；完整验收还需关闭阻塞审核问题并记录用户验收依据。

缺环境或缺执行授权时交付完整配置、步骤和待办，明确“待部署/待验证”，不得声称完整流程已跑通。
