# 审核标准

按收到的产物选择审核阶段，不自动扩大到全流程。

## 按阶段核对

| 阶段 | 审核重点 |
|---|---|
| 需求 | 来源和确认依据是否真实，文档/原型/模板是否冲突；字段、数据来源、状态、权限、异常、验收是否闭环；用[需求契约](需求契约.md)，涉及专项能力时用[专项检查](专项需求检查.md) |
| 架构 | 默认 NORMAL 的能力是否经源码查证；是否偷偷切 CUSTOM 或裁剪功能；主体ID、快照/实时、数值/正文、状态映射、集成、权限与事务边界是否明确 |
| 开发 | 对照确认需求和实际 diff，核对表单/模型/路由绑定、服务端校验、越权、重复提交、旧状态回写、精度和失败处理；复用[实现清单](实现与验证清单.md)的相关项 |
| 测试/交付 | 用例是否覆盖确认规则及反例；环境、代码/模型版本与报告是否一致；证据文件是否存在并支持结论；跳过/阻塞是否被误报为通过；原型模拟是否被当成运行验证 |

测试证据审核时按需读取[测试与留痕标准](测试与留痕标准.md)，架构或代码审核时按需读取[能力地图](能力地图.md)。

## 审核输出

只报告可定位、可解释的问题：`编号 | 严重度 | 需求编号/文件位置 | 证据 | 影响 | 修改建议或待确认方案 | 复核状态`。严重度按阻塞交付、重要缺陷、一般问题区分；风格偏好不要上升成缺陷。

结论使用“本次范围内通过 / 需修改 / 证据不足”，附审核范围、版本和未验证项；存在关键业务冲突或关键证据缺失时，不给无条件通过。没有问题就明确说明，不为凑数制造问题。审核意见不是用户的业务确认，也不是发布授权。

复核按问题编号逐项核实修改与证据，不只看开发者口头声明；已解决项记录依据，新增影响补充回归建议。

审核交接时按[任务文档与交接标准](任务文档与交接标准.md)检查权威目录、文件排序、可开发状态、需求/方案修订对应关系和过期处理；任务清单缺依赖或验收条件、开发未读当前方案、证据对应旧版本均须明确指出。
